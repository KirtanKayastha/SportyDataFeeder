# API Reference

Base URL: whatever host/port `uvicorn app.main:app` is bound to (default `:8000`, or
`:8010` in the two-feeder local-demo setup described in `README.md`/`DEMO_RUNBOOK.md`).
Interactive docs are auto-generated by FastAPI at `GET /docs` (Swagger UI) and
`GET /openapi.json`.

## Authentication (applies to almost everything below)

`app/main.py:require_feeder_secret` is an `@app.middleware("http")` function that runs
before every request. It checks `request.url.path` against an exemption set:

```python
_AUTH_EXEMPT_PATHS = {"/health", "/docs", "/openapi.json", "/admin", "/admin/"}
```

For any other path, it reads the `X-Feeder-Secret` header and compares it to
`get_settings().FEEDER_SECRET` using `secrets.compare_digest` (timing-attack-safe). A
missing or wrong value returns:

```json
HTTP 401
{"detail": "Missing or invalid X-Feeder-Secret header"}
```

Note that `/admin` is exempt so the *static HTML page itself* loads without the header,
but every API call the page's own JavaScript makes still supplies the secret (entered by
the operator into a field on the page) — so the actual data routes remain protected.

There is no per-user authentication, no roles, no scopes — one shared secret gates the
entire API. See `CONFIGURATION_DEPLOYMENT.md` for the security implications.

## Health & operational endpoints (`app/main.py`)

### `GET /health`
No auth required.
- Executes `SELECT 1` against the configured database; on failure returns
  `503 {"detail": "Database connection failed: <exception>"}`.
- On success:
```json
{
  "status": "ok",
  "database": "up",
  "simulations_running": 0,
  "models": {
    "outcome_model": true,
    "outcome_v2": true,
    "outcome_v2_basketball": false,
    "event_rates": true,
    "event_rates_players": 842
  }
}
```
`simulations_running` calls `app.services.simulation.running_count()` (counts
`SimulationState`s with `status == "running"` in the in-memory registry).

### `GET /admin`
No auth required. Serves `app/static/admin.html` as `text/html` if the file exists;
`404 {"detail": "Admin panel not built"}` otherwise. This is a single self-contained
static console (no build step, no framework) for operators to drive the API by hand.

### `POST /models/reload`
Auth required. Re-runs `_load_models_into_state` — re-reads every `.pkl` from
`models_pkl/` into `app.state` without restarting the process. Designed to be called by
`scripts/refresh_bundles.py --reload-url ...` after a cron rebuild.
```json
{"reloaded": true, "models": {"outcome_model": true, "outcome_v2": true, ...}}
```

## `/simulate` and friends (`app/routers/simulation.py`)

| Method | Path | Auth | Body | Success | Notes |
|---|---|---|---|---|---|
| POST | `/simulate` | yes | `SimulateStartRequest` (see below) | `202 SimulateStartResponse {match_id, status: "running", status_url}` | 409 if that match already has a running simulation; 422 if `match_id` omitted and `home_team_id`/`away_team_id`/`sport_id` also incomplete, or teams identical, or sport unresolvable; 404 unknown match/team |
| GET | `/simulate` | yes | — | `200 [SimulationStatusRead]` | Every simulation the process knows about (running + recently ended), most-recently-active first — powers the admin panel's live monitor |
| GET | `/simulate/{match_id}/status` | yes | — | `200 SimulationStatusRead` | 404 if no simulation has ever been started for this match in this process's lifetime (state is **in-memory only** — a restart wipes it, see `IMPROVEMENTS.md`) |
| POST | `/simulate/{match_id}/stop` | yes | — | `200 {"detail": "Stop requested..."}` | Sets `stop_requested`; the loop checks it once per minute and halts after the *current* minute finishes, not instantly. 409 if nothing is running for that match |
| POST | `/matches/{id}/replay-push` | yes | — | `200 ReplayPushResult {match_id, delivered, events_sent}` | Re-sends every stored event for the match in one payload. 422 if the match has no `sporty_match_id` entity link yet |

`SimulateStartRequest` body:
```json
{
  "match_id": 7,                       // OR the three fields below to auto-create a match
  "home_team_id": null,
  "away_team_id": null,
  "sport_id": null,
  "sporty_match_id": null,             // optional — upserted into entity_links if given
  "sporty_home_team_id": null,
  "sporty_away_team_id": null
}
```
If `match_id` is omitted, the router creates a new `Match` row with `status="scheduled"`
from the team/sport fields before starting the simulation.

`SimulationStatusRead`:
```json
{
  "match_id": 7, "status": "running",           // running | finished | stopped | error
  "current_minute": 34, "total_minutes": 90,
  "home_score": 1, "away_score": 0,
  "events_inserted": 12, "push_failures": 0,
  "error": null
}
```

| Method | Path | Auth | Body | Success | Notes |
|---|---|---|---|---|---|
| POST | `/imports/nba` | yes | `ImportNBARequest {csv_path, gameweek?, season?}` | `200 {status: "ok", result: {...}}` | 404 file not found; 400 missing required columns (`TEAM`/`PLAYER`) or sport not seeded |

Both requests accept relative or absolute filesystem paths — **there is no file upload
endpoint**; the CSV must already exist on the server's filesystem (a deliberate,
low-effort design choice appropriate for an operator-driven demo tool, but a real
multi-tenant deployment would need a proper upload path — see `IMPROVEMENTS.md`).

## `/predict` (`app/routers/predict.py`)

| Method | Path | Auth | Body | Success | Notes |
|---|---|---|---|---|---|
| POST | `/predict` | yes | `PredictRequest {match_id}` | `200 PredictResponse` | See `MODELS.md` for the full v2→v1→heuristic fallback chain. Always inserts a `MatchPrediction` row; pushes to the Sporty backend only if the match is linked |
| GET | `/predict/metrics` | yes | — | `200 {...}` | Scores every stored prediction whose match has since finished — accuracy/log loss/Brier/ECE + a 10-bin calibration table, grouped by `model_version` |
| POST | `/predict/metrics/push` | yes | — | `200 {pushed: bool, metrics: {...}}` | Computes the same scorecard and pushes it to the Sporty backend's `/api/v1/feed/model-metrics` (manual trigger; the simulation loop also does this automatically on match finish) |

`PredictResponse`:
```json
{
  "match_id": 7,
  "home_win_prob": 0.51, "draw_prob": 0.24, "away_win_prob": 0.25,
  "model_version": "outcome_v4_elo_sot",
  "home_strength": 0.62, "away_strength": 0.48,
  "pushed": true
}
```
`home_strength`/`away_strength` are `[0,1]`-scaled: for the v2 Elo path they're a sigmoid
of the raw Elo rating (see `MODELS.md`); for the v1/heuristic fallback path they're
`compute_team_strength()`'s mean-form-index output.

## `/demo/launch` (`app/routers/demo.py`)

| Method | Path | Auth | Body | Success | Notes |
|---|---|---|---|---|---|
| POST | `/demo/launch` | yes | `DemoLaunchRequest` (see below) | `200 {status, mode, feeder_match_id, sporty_match_id, players_linked, players_in_lineup, draftable_players, prediction, fantasy_demo, status_url, frontend_url}` | One call that: (1) schedules the fixture on Sporty, (2) registers or resolves the simulated lineup as backend players and links each, (3) pushes the per-team starting lineups, (4) optionally pushes an outcome prediction, (5) optionally creates a throwaway demo fantasy lineup, (6) optionally starts the simulation. 404 unknown match; 409 already simulating; 422 unknown sport or missing teams |

`DemoLaunchRequest` body and defaults:
```json
{
  "match_id": 16,
  "fantasy_demo": true,       // auto-create a throwaway demo user's fantasy lineup
  "simulate": true,           // false = "prepare" mode: schedule+register+predict only
  "push_prediction": true,
  "resolve_existing": false,  // true = map onto players real users already drafted, by name
  "featured_players": []      // names to force into the simulated lineup
}
```
Individual sub-steps (lineup push, prediction push, demo-setup) are wrapped in their own
`try/except` and only log a warning on failure — a partial failure never blocks the
overall launch or the live feed (see `ARCHITECTURE.md` §Resilience patterns).

## Error-handling conventions across the whole API

- `404` — the referenced entity id doesn't exist. Always via a shared `_not_found(entity,
  id)` helper duplicated (not shared as an import) across `sports.py`, `teams.py`,
  `players.py`, `matches.py`, `events.py`, `simulation.py` — each router defines its own
  identical copy rather than importing one from a shared module (a minor duplication, see
  `IMPROVEMENTS.md`).
- `400` — validation failures the database itself could also reject via a constraint
  (duplicate name, mismatched sport, self-referential match) — caught proactively where
  possible, and via `except IntegrityError` as a second line of defense on every create
  endpoint.
- `409` — a genuine state conflict: simulation already running for this match, or trying
  to stop one that isn't running, or the Sporty backend reports the linked match is
  currently live.
- `422` — request body fails Pydantic validation (handled entirely by FastAPI, no custom
  code) OR (custom, `status.HTTP_422_UNPROCESSABLE_CONTENT`) a sport name can't be
  resolved to a known `SportType`.
- `401` — missing/incorrect `X-Feeder-Secret` (middleware-level, before any router runs).
- `503` — only from `GET /health`, when the database itself is unreachable.

## Explain Like I'm New

Every endpoint needs one secret password in a header (`X-Feeder-Secret`) — think of it as
a single house key shared by the feeder and the Sporty backend, not individual keys per
user. Most endpoints are ordinary "add/list/remove a row" CRUD. The interesting ones are
`/simulate` (kicks off a fake live match that plays itself out minute-by-minute in the
background) and `/demo/launch` (a "do everything" button that sets up and starts a demo
match with one API call instead of five).
